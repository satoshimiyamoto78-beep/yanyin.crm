# Архитектура платформы: международно, надёжно, на годы

> 19 ноября 2026. Решение: ADR-019. Интерактивная схема: https://claude.ai/artifact/JHtzfu3FzYajVA31HJywU2. Дополняет `02-architecture.md` (дерево системы и цепочки процессов) и ADR-009 (страна как модуль).

## 0. Задача

yanyin — подписочный продукт, который подключает любое заведение в любой стране. Владелец сам подключает свою оплату, свои чеки и налоги, свои программы (Excel, Google Sheets, 1С и другие). Система работает как швейцарские часы: без сбоев, быстро, безопасно, обновляется без простоя и служит годами.

Отсюда три требования, которые важнее выбора хостинга:

1. **Ядро не знает страну.** Всё местное подключается модулями.
2. **Сбой снаружи не останавливает зал.** Ни упавшая 1С, ни пропавший интернет в заведении.
3. **Ничего непереносимого.** Любую часть можно увезти к другому поставщику или на свои серверы без переписывания продукта.

## 1. Ядро и модули

```
                ┌──────────────────────────────────────────┐
                │                 ЯДРО                      │
                │  заказы · столы · меню · склад · смены    │
                │  деньги · роли · квесты · Ян · события    │
                └───────┬──────────┬──────────┬────────────┘
                        │ порты (общие интерфейсы)
        ┌───────────────┼──────────┼──────────┼───────────────┐
   Оплата          Фискальный     Налоги      Выгрузка      Оборудование
   (PaymentPort)   чек (Fiscal)   (TaxPort)   (ExportPort)  (DevicePort, ADR-012)
        │               │            │            │
  VN: VietQR, MoMo  VN: e-invoice  ставки VAT  Excel/CSV, Google Sheets,
  TH: PromptPay     UZ: ОФД        и сервис-   1С, вебхуки, API
  UZ: Click, Payme  RU/KZ: ОФД     сбор по
  EU: Stripe, Adyen …              стране
```

- Ядро оперирует общими понятиями: «оплата», «чек», «налог», «выгрузка». Конкретный провайдер реализует порт: `PaymentPort.createIntent`, `capture`, `refund`, `webhook`; `FiscalPort.issueReceipt`, `cancel`; и так далее.
- **Пакет страны** (`packages/country-<код>`) собирает адаптеры, налоговые правила, формат чека, валюту, языки и праздники. Новая страна — новый пакет; ядро не меняется.
- **Адаптер провайдера** (`packages/integrations/<провайдер>`) — один на сервис, переиспользуется в разных странах (Stripe работает в десятках стран).
- Заведение в настройках выбирает страну, затем включает нужных провайдеров и вводит свои ключи. Ключи хранятся зашифрованными, сервер их никогда не показывает.

## 2. Интеграции в три уровня

| Уровень | Что | Кто пишет | Когда |
|---|---|---|---|
| **1. Встроенные** | Excel/CSV по кнопке и по расписанию; живая синхронизация с Google Sheets (вход через Google); обмен с 1С по её стандартным форматам (CommerceML, OData) | мы | Excel и Sheets — к пилоту, 1С — после |
| **2. Открытый API и вебхуки** | REST API с ключами и правами; вебхуки на каждое событие (`order.paid`, `stock.low`…) с подписью и повторами | заведение или его подрядчик | после пилота |
| **3. Коннекторы** | Zapier, Make, n8n: через них тысячи сервисов, которые мы никогда не напишем сами | платформы-посредники | после API |

Позже на этой основе — **маркетплейс приложений** (как у Shopify): сторонние разработчики подключают свои модули через OAuth.

## 3. События и очередь: сбой снаружи не ломает зал

Каждое действие в ядре — событие в `domain_events` (уже заложено в домене). Внешний мир получает события только через очередь:

```
действие в зале ──► транзакция в БД: запись + событие (outbox)
                                   │
                                   ▼
                     очередь ──► воркеры интеграций
                                   │   повторы с паузой, защита от дублей,
                                   │   «мёртвые» сообщения отдельно
                                   ▼
                        1С · Google Sheets · вебхуки · фискальный чек
```

- Запись и событие пишутся одной транзакцией (паттерн outbox): событие не теряется, даже если сервер упал сразу после заказа.
- Воркер повторяет отправку с растущей паузой. Каждый запрос несёт ключ идемпотентности: повтор не создаёт второй чек или второй платёж.
- Сообщение, которое не прошло после всех повторов, попадает в отдельный список, а админ видит «Выгрузка в 1С не прошла, повторить».
- Пока внешний сервис лежит, заказы, кухня и оплата работают; выгрузка догоняет позже.
- Фискальный чек — особый случай: если закон требует чек до выдачи, адаптер страны решает, ждать ли ответа или выдавать с отложенной фискализацией (как разрешено в стране).

## 4. Регионы-ячейки

```
                    ┌───────────────────────────────┐
                    │  ОБЩИЙ КОНТУР (control plane) │
                    │  аккаунты · подписки · биллинг │
                    │  каталог заведений → регион    │
                    └──────┬───────────────┬────────┘
                           │               │
              ┌────────────▼───┐     ┌─────▼──────────┐
              │ Ячейка «Азия»  │     │ Ячейка «Европа»│  … новые по мере роста
              │ Сингапур       │     │ Франкфурт      │
              │ БД, файлы,     │     │ БД, файлы,     │
              │ realtime,      │     │ realtime,      │
              │ воркеры        │     │ воркеры        │
              └────────────────┘     └────────────────┘
```

- Ячейка — полная независимая копия системы со своей базой. Заведение «живёт» в одной ячейке; все его данные там.
- Общий контур хранит только аккаунты, подписки и адрес ячейки каждого заведения.
- **Что это даёт:** скорость (данные рядом), законы любой страны (если требуется хранить данные в стране — поднимаем ячейку там), сбой одной ячейки не трогает другие, обновления выкатываются по ячейкам.
- **С чего начинаем:** одна ячейка (Сингапур, ближайший регион к Вьетнаму, Таиланду, Лаосу). Но с первого дня у каждой организации есть поле `region`, а код получает подключение к базе через него. Вторая ячейка — новая копия, а не переписывание.

## 5. Работа без интернета в заведении

Самый частый реальный сбой для кассы — пропал Wi-Fi.

- **К пилоту:** заказы, отметки кухни и оплаты наличными пишутся сначала на устройство (очередь в IndexedDB) и уходят на сервер, когда связь вернётся; на экране видно «Нет связи, 3 действия ждут отправки». Рекомендуем заведениям резервный 4G-роутер.
- **Позже, если сбои частые:** локальная синхронизация (класс решений вроде PowerSync поверх нашего Postgres) или хаб в сети заведения, как у Toast.
- Оплата картой без связи зависит от терминала банка; это решает адаптер оборудования (ADR-012).

## 6. Надёжность: порядок выпуска и наблюдение

- **Окружения:** разработка → тестовый стенд (копия продакшена на демо-данных) → продакшен.
- **Проверки на каждый коммит:** типы, линтер, тесты домена, тесты изоляции заведений (RLS), сборка. Без зелёных проверок изменение не выходит.
- **Постепенный выпуск:** сначала одна ячейка или часть заведений, потом все. Новые функции за флагами (`feature_flags`), их можно выключить без релиза.
- **Миграции базы только обратно совместимые:** сначала добавляем, потом переключаем код, потом удаляем старое. Старая и новая версии могут работать одновременно, поэтому обновление идёт без простоя.
- **Наблюдение:** ошибки (Sentry), доступность и скорость по ключевым путям (заказ → кухня, оплата), журнал событий. Тревога приходит нам раньше, чем жалоба клиента.
- **Цель доступности:** 99,9 % в месяц (до 43 минут простоя), публичная страница статуса.
- **Бэкапы:** с восстановлением на любую минуту назад (PITR); раз в месяц пробное восстановление на стенде.
- **Деньги:** только целые числа в минимальных единицах валюты с кодом валюты; ключ идемпотентности на каждый платёж и возврат; ежедневная сверка с провайдером.

## 7. Безопасность

- **Изоляция заведений** на уровне базы (RLS по `organization_id`) и автоматические тесты, что одно заведение не видит другое.
- **Права проверяются на сервере**, а не только скрытием в интерфейсе (ADR-017).
- **Данные карт мы не храним и не видим:** их обрабатывает платёжный провайдер (токены, платёжные страницы). Так мы почти выходим из-под тяжёлых требований PCI DSS.
- **Вход:** двухфакторный для владельцев и админов; планшеты станций без логина, по коду (уже в UI).
- **Секреты** (ключи провайдеров заведений) — зашифрованы, в хранилище секретов; доступ только у воркера интеграции.
- **Журнал действий** (кто что изменил: цены, возвраты, права) — неизменяемый.
- **Обновление зависимостей** автоматически, с проверками.
- **Перед запуском** — внешний аудит (пентест). Для крупных сетей позже — SOC 2 и ISO 27001.
- **Персональные данные:** минимум данных гостя, удаление по запросу, документы о передаче данных по законам страны ячейки (во Вьетнаме — закон № 91/2025/QH15).

## 8. Технологии

| Часть | Выбор | Почему и как уйти, если понадобится |
|---|---|---|
| Приложение | Next.js (TypeScript), один код на все поверхности | Работает на Vercel, в Docker на любом сервере, в облаке |
| База, вход, realtime, файлы | Supabase: отдельный проект на каждую ячейку | Открытый код и обычный Postgres; можно развернуть у себя |
| Очередь и фоновые задачи | Очереди в Postgres (Supabase Queues, pgmq); при росте — отдельный движок фоновых задач | Очередь живёт в той же базе: меньше движущихся частей |
| Хостинг приложения | Vercel, регион рядом с ячейкой | Замена — контейнер на любом облаке, код не меняется |
| Ошибки и мониторинг | Sentry, проверки доступности | Стандартные протоколы (OpenTelemetry) |
| ИИ (Ян) | Claude API с сервера, ключ не уходит на устройство | Лимиты и учёт расходов по заведению (уже в `yanyin.core`) |

Чего избегаем: закрытых баз без SQL (Firebase, Convex), функций, которые работают только у одного хостинга, хранения логики в интерфейсе.

## 9. Порядок работ

**До пилота:**
1. Порты и пакет страны `country-vn` (VietQR, MoMo, e-invoice).
2. Схема БД с `organization_id`, `region`, RLS и тестами изоляции.
3. События + outbox + очередь + воркеры с повторами.
4. Первая ячейка (Сингапур), тестовый стенд, проверки на каждый коммит.
5. Очередь действий без интернета на устройствах.
6. Бэкапы с PITR, Sentry, проверки доступности.
7. Выгрузка в Excel/CSV и Google Sheets.

**После пилота:** открытый API и вебхуки → Zapier/Make/n8n → 1С → вторая ячейка → маркетплейс приложений → SOC 2 / ISO 27001.
